# Humanoid crowd simulation: motion-backend handoff

**Date:** September 30, 2026  
**Status:** Implementation plan; no local throughput measurements have been collected.

## Goal and order of work

Build stochastic, reactive human crowds for training a LiDAR-conditioned humanoid traversal policy in **4,096 parallel environments**. Prefer **batched online motion generation**, allowing new motions to be generated from simulator-state-dependent decisions rather than restricting humans to a fixed library.

**Benchmark ARDY and KIMODO → choose a backend → optionally build a motion graph → implement the simulator behavior model.** Do not begin by training a new motion prior or building a custom human rig. Keep MotionBricks outside this initial comparison.

## 1. Establish working backends

**ARDY:** Start with `ARDY-Core-RP-20FPS-Horizon8` and `ARDY-Core-RP-20FPS-Horizon40`: respectively 0.4-second and 2-second human-motion horizons. The current README still lists SOMA checkpoints as forthcoming; do not confuse a supported model nickname with released weights. Resolve the existing Core-to-human-mesh integration before committing to this backend. [1]

Use `Ardy.autoregressive_step()`, which accepts batched text features, history, and constraint tensors. Inspect output lengths: returned motion includes history, which must not count as newly generated motion. [2]

**KIMODO:** Start with `Kimodo-SOMA-RP-v1.1`. Its Python API supports independent batched prompts, durations, and per-sample constraints. Keep `multi_prompt=False` for independent humans; multi-prompt mode denotes sequential segments, not independent batch entries. [3], [4]

Prototype KIMODO continuation using a short executed-history prefix as constraints. Its documented sequential generation conditions on preceding frames, but closed-loop continuation quality still needs testing; do not equate offline stitching with validated online control. [5]

For both, implement a thin adapter:

```text
Generate(executed_history, prompt_embeddings, future_constraints, seeds)
    -> new_root_motion, joint_rotations, contacts, frame_rate
```

Preserve native skeleton metadata and coordinate conventions. Translate desired velocity into supported root-path/waypoint constraints where needed; do not assume a direct velocity-tensor API.

## 2. Benchmark usable motion, not just generation speed

Record GPU model/count/VRAM, driver, CUDA/PyTorch versions, repository commits, checkpoint revisions, precision, and acceleration settings. Start on available hardware; do not extrapolate 4090 results to a different training GPU. Record whether 4,096 environments are per GPU or distributed.

Use the following **initial, configurable sweep**, not an exhaustive Cartesian product:

| Dimension | Initial tests |
|---|---|
| Batch size | 1, 16, 64, 256, 1,024, 4,096; microbatch when necessary |
| Humans per environment | 1 first, then 4 and 8: total population is `4096 × humans_per_env` |
| Motion horizon | ARDY native horizons; KIMODO supported short/medium lengths, initially 1, 2, 5 seconds |
| Replanning | Buffer refill; periodic 0.2, 0.5, 1, 2 simulated seconds; stochastic switches |
| Sampling | Default settings first, then valid reduced-step settings with quality checks |
| Workload | Fresh starts, steady continuation, heterogeneous prompts/paths, burst switches |

Cache embeddings for a small behavior/style prompt bank and remove repeated text encoding from the steady-state path. Use lower-level integration where necessary; measure any adapter changes. Keep tensors on-device where practical. Exclude GUI, export, and model loading from steady-state timing; report startup separately.

Warm up each configuration. Measure synchronized wall time and GPU time, including constraint construction, history encoding, decoding, postprocessing, and transfers. Test cleanup enabled and disabled: KIMODO recommends postprocessing when constraint/contact accuracy matters. [5] Profile CPU loops and synchronization rather than assuming tensor batching guarantees end-to-end scalability.

For batch size $B$, **new** generated duration $H$, batch wall time $T_B$, and fraction $u$ actually consumed before replacement/reset:

$$
R_{\mathrm{usable}} = u\frac{BH}{T_B}.
$$

This is usable human-motion seconds per wall-clock second. If each environment advances $S$ simulated seconds per wall-clock second and contains $m$ humans, demand is

$$
R_{\mathrm{required}} = 4096\,m\,S.
$$

Use the cached-motion baseline or requested target for $S$ when budgeting. Use measured sums for heterogeneous batches. Sufficient isolated generation capacity is necessary, not sufficient: GPU contention and scheduling still matter. Report discarded predictions, p50/p95 latency, peak VRAM, total microbatched population-refresh time, and achieved simulator throughput.

Compare end-to-end runs against the **same humans, geometry, and sensors replaying cached motion**. Include mesh skinning, collision queries, LiDAR, and robot-policy computation. Synchronous simulation may pause for inference: wall-clock stalls slow training, whereas committed buffered frames delay reactions in *simulation time*. Report these separately.

Test long continuations and mid-motion stop/start/turn commands. Measure path/speed error, foot sliding, pose/velocity discontinuities, penetrations, command-response delay, and failures. Branch the same executed history into different continuations; future random decisions must not alter the past.

## 3. Choose using measured tradeoffs

Select based on **end-to-end throughput, response delay, continuation quality, VRAM, and existing mesh compatibility**, not single-character “real-time” claims. Report a speed–quality comparison at comparable task demands; equal diffusion-step counts are not necessarily comparable quality.

Make acceptable slowdown and response-delay limits configurable. If no limits are specified, report achieved performance rather than inventing a pass threshold. Prefer online generation if it meets the eventual budget. First try microbatching, cached embeddings, supported acceleration, and bounded history before introducing a graph or distillation.

## 4. Optional motion-graph fallback

Only build this if online generation fails the measured budget or continuation requirements. Generate clips/bridges offline and expose the same backend interface. Match short boundary windows using pose, velocity, heading, and support-foot/contact state—not isolated keypoint positions. Preserve frequent transition opportunities so clip length does not force long reaction delays.

A hybrid is acceptable: cached ordinary locomotion plus online unusual transitions. Keep behavior decisions independent of this choice.

## 5. Simulator behavior and runtime scheduling

Separate **intent → local steering → body-motion generation**. The simulator-state-based decision rule chooses behavior and targets; the motion model realizes them. Do not assume either generator understands scene obstacles without explicit constraints and validation.

Maintain per-human goal, behavior mode, elapsed mode time, persistent traits, perceived neighbor states, executed history, and a future-motion buffer. Begin with travel, wait, yield, and reroute. Distinguish non-yielding pedestrians from deliberately intercepting pedestrians; reserve bounded interception for labeled stress tests.

Use duration-aware switching, for example

$$
P(\mathrm{switch})=1-\exp[-\lambda_b(\tau,c,\theta)\Delta t],
$$

where $\tau$ is mode age, $c$ perceived context, $\theta$ persistent traits, and $\Delta t$ **simulated** elapsed time. Sample traits once per person/episode; avoid frame-independent personality changes. Include minimum dwell times, limited acceleration/turning, and configurable perception delay. Initially these are controllable heuristics, not calibrated human-behavior statistics.

Gather humans needing refill or a changed plan, bucket compatible requests, generate in batches, and scatter results back. Refill even without a behavior switch. Use per-human random streams, independent of batch order. Invalidate stale predictions on switches/resets; condition on actually executed motion. Implement synchronously first, then consider overlap without leaking future simulator state or silently extending behavioral delays.

## 6. Human geometry and deliverables

Reuse an existing body model and skinning pipeline. For KIMODO/SOMA, evaluate supplied SOMA-X low-resolution and extra-low-resolution meshes before custom simplification. [6] Keep LiDAR geometry distinct from physics collision representation; verify the chosen engine supports the intended animated geometry. Initially use kinematic humans if contact terminates an episode; physical pushing requires an additional response model. Validate simplified meshes against sensor error and missed collisions.

Deliver a reproducible benchmark script/configuration, raw CSV/JSON measurements, a short backend recommendation with rollout videos, and the selected adapter. Then deliver an optional graph only if justified, followed by the batched behavior controller and a simulator smoke test. Keep all unmeasured assumptions explicit.
